## 0. TL;DR (numbers)

- **Fixture LH baseline after the harness fix (`baseline2`, "/", PL, no /en redirect): mobile TBT 558–991 ms, and 90–95 % of it is `vendor-react` long tasks after FCP** (551/616, 630/558, 942/991 ms of the TBT sum, 9–12 tasks per run). Desktop TBT 16–105 ms, again only `vendor-react`. Hydration plus what runs right after it is the TBT budget. The CSS/HTML parse tasks come before FCP and don't count toward TBT.
- Own CDP traces at 4× CPU, using an in-process fixture backend so the browser's PostgREST calls succeed as in production: **React stays 60–80 % busy from 1.5 s to 7.5 s.** Only ~0.5 s of ~3.0–3.3 s of React work comes before the root commit (`__nesAppReady`). **~2.7 s runs after it.** That later work is lazy-boundary hydration, the device-switch re-render and refetch re-renders.
- Post-hydration main-thread hot spots at 4×. Each item is a single task:
  1. root hydration pass: one non-yielding **361 ms** task;
  2. `--sticky-header-h` written on `:root`: full recalc of **874 elements, 137–177 ms**, plus a forced layout (`getBoundingClientRect` in an effect, 138 ms inclusive);
  3. refetch + ticker animation: recalc 115–196 ms **+ full layout 143–192 ms**;
  4. mobile device-switch commit: **25 `<style>` swaps + recalc of 797 elements, 166–198 ms**.
- **Production network after hydration (prod LH JSON): 6 PostgREST + 6 CORS preflights + 1 serverFn POST.** The other 8 "Fetch" entries are Google collect beacons. The evidence pack's "15 PostgREST" is wrong. The fixture with a dead backend shows 18+18, because failed queries are retried. Every one of the 7 app requests has an identifiable cause and a fix (§3).
- Region experiment (fixture variants): dropping sections 2–8 and most of the footer (−727 DOM elements, −45 %) cut React work only **~25 %** (3.0 → 2.2 s at 4×), style −48 %, layout −70 %. **Hydration cost is dominated by per-page fixed work: header, first section with the slider, overlays, effects, the storm and the device switch. Per-element cost matters less.** Islands are necessary but not sufficient. The storm and the device switch must go first, because they also force islands to client-render.

## 4. Deferred-hydration islands (task 2)

### 4.1 Mechanism (React 19)

- During hydration, a `<Suspense>` boundary whose content suspends is **left dehydrated**: the server HTML stays visible and in the DOM, and React retries it later at a Retry lane (time-sliced). Today's `withSuspense` (`lazySuspense.tsx:37-47`) gets this only by accident, while a lazy chunk is in flight. The chunk is requested immediately because `React.lazy` starts `import()` on the first hydration render.
- An island adds a **client-only gate inside an existing boundary**: `use(islandGate(id))` throws until a trigger resolves a module-level promise keyed by the section id. The server renders the children directly, so the SSR HTML is unchanged except for a `<!--$-->…<!--/$-->` pair around static sections that have no boundary today. The gate's DOM anchor is the section root `[data-sec-id]`, already present in the server HTML (16 occurrences on prod "/").
- **Hard precondition — no update may reach a dehydrated island.** A props or context change reaching a dehydrated boundary is fatal. If it is a Default/Sync lane update, React tries selective hydration, the gate still suspends, and React **client-renders the boundary**. That deletes the server HTML and shows the fallback (`null` → collapse → CLS, `lazyWidgets.tsx:20-22` warns about exactly this). Transitions are safe because React delays them. Today's sources of such updates:
  - (a) AuthProvider — already uses `startTransition` (`useAuth.tsx:259-268`, test `hooks/__tests__/authHydration.test.tsx`);
  - (b) BuilderRenderer device switch — a transition, but it forces hydration of every boundary it touches and is restarted on every ping (H6 is a precondition);
  - (c) refetched settings/tokens/layout data. Query updates don't reach unmounted subscribers, but a changed value read at island hydration time **mismatches the SSR HTML**, which also triggers a client render (H1/H2/H3 are preconditions);
  - (d) i18n/theme provider value changes after mount — must be audited (ThemeProvider, `I18nextProvider`, `AccessContext` via `useAccessContext` = auth-derived).
- Discrete events on a dehydrated, gated island are **not replayed**. A link click falls back to native navigation (MPA), which is acceptable. A button click would be lost, so islands also listen to `pointerdown`/`touchstart`/`focusin`/`keydown` on their own root (capture phase) and resolve the gate before `click` fires.

What changes for SSR budgets and streaming. Nothing on the server path: the island is client-only (`IS_SSR` branch like `StreamingSection`). `hasSsrQueryData`, `homeSsrDeadline` and `ServerSectionGate` stay as they are, and the 16 streamed boundaries keep streaming. When a streamed boundary's `$RC` swap lands before hydration it becomes a normal dehydrated boundary and the island gate applies. When it lands after the root commit it is already in "pending dehydrated" state, and React hydrates it on the gate retry.

CLS: zero by construction, as long as the precondition holds. Fallback safety net: island boundaries use `SectionStreamSkeleton minHeight={estimateSectionHeight(section)}` (`sectionStreaming.tsx:170-197`) instead of `null`, so an accidental client render reserves its height.

SEO: identical HTML. Crawlers, which get `allReady`, see everything. JSON-LD is untouched.
