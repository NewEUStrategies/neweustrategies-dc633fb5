## 0. TL;DR

- Production `/` is 569 KB raw / 78.0 KB gzip (Lighthouse saw 89.4 KB transfer, **gzip, not brotli**). Measured by component: dehydrated state 125.8 KB / 28.3 KB gz (the largest gzip item, 36 %), inline CSS 134.5 KB / 18.9 KB gz, main markup 204 KB / 13.4 KB gz, header markup 49 KB / 7.7 KB gz, footer markup 30 KB / 5.0 KB gz, head links/meta 13.4 KB, other inline scripts 10.1 KB.
- If we apply the proposals to the saved HTML, it shrinks to **337 KB raw / 45.6 KB gz** with the core set (HW-1…HW-5) and to **297 KB / 42.2 KB gz** with the stretch items (HW-6, HW-8). The fixture goes 382 → 234 KB raw, 50.3 → 28.9 KB gz. The "≤ 200 KB raw / ≤ 35 KB gzip" target **cannot be reached on production with safe projections**. Getting there would mean dropping visible markup: the 37 KB desktop header that is display:none on mobile, and non-active slider slides. Both conflict with SEO, CLS or hydration (§6).
- **Measured metric effect**: interleaved no-JS Lighthouse runs of production-HTML variants served through the artifact (§7):
  - Mobile FCP and LCP do not move (Δ ≈ 0 ± 40 ms, N = 4–5).
  - Mobile TBT goes from 138–192 ms to 0–80 ms (median −130 ms). These are document parse/style long tasks.
  - Main thread goes from 1 508 ms to 1 260 ms (−250 ms) and Style & Layout from 401 ms to 276 ms.
  - Desktop SI drops ~−90 ms and TBT goes 16 → 0 ms.
  - Sensitivity check: +150 KB of incompressible bytes in the document add +0.75 s FCP and +0.9 s LCP (5–6 ms/KB). So document bytes count in Lantern once the document is the long pole. In today's regime (document 37–80 KB against 79 KB CSS) a 25–32 KB cut does not move FCP.
- **Conclusion for the plan**: html-weight is a **TBT / main-thread lever**, not an FCP/LCP lever. Today the document parse tasks (~1.2–2.2 s simulated) sit **before** the simulated FCP (5.0 s), so they are hidden in FCP's CPU part and are not counted in TBT. Once boot-js moves boot after LCP (FCP ≈ 1.4 s), the same tasks fall **into the TBT window**: this is part of the "+530…770 ms long-task excess" boot-js warns about. That is when −130 ms TBT counts, roughly +3–5 mobile points. There are secondary FCP/LCP wins of −30…50 ms from JS bytes: the static CSS strings that live inside the entry and sliderVariants chunks.

Fixture: 75 297 → 46 380 raw, 11 903 → 7 819 gz. The fixture has no menu or srcset data, so the newsletter, settings and CSS-input steps dominate.

Why a projection must live in the **queryFn / server function** and not in `dehydrate`: `setupRouterSsrQueryIntegration` calls `dehydrate(queryClient, dehydrateOptions)`, and react-query's `serializeData` is a single global function with no access to the query key (`node_modules/@tanstack/router-ssr-query-core/dist/esm/index.js`, `dehydrate` call). If the server projected only at dehydration time, the client's later refetch would bring the full shape, and SSR would have rendered from the full shape. Both cases risk divergence. Projecting in the query function gives byte-identical SSR, hydration and refetch. Locale projection is safe only for keys that contain `lang`. The language switch is a soft `router.navigate` (`src/lib/i18n/switchUiLanguage.ts:163`), so lang-less keys would keep PL-only data after a switch.

## 6. What does not get to 200 KB / 35 KB (and why we should not force it)

- After core and stretch: 297 KB / 42 KB gz. The rest is visible content markup (main 141 KB raw / 10 KB gz) and the builder docs needed for hydration (home 16.4 KB, header/footer 10 KB).
- Next levers, both with trade-offs:
  - (a) Device-class SSR: drop the 37 KB desktop header from mobile documents. This needs a cache-key split on device class and leaves the mobile document without the desktop nav links. Human decision; not recommended for this PR.
  - (b) Render only the active slide of each slider in SSR: about 40 KB raw / 4 KB gz across 4 sliders. This changes the hydration tree and slider CLS behaviour (hydration/lcp-path territory).

Interpretation:

1. In the current regime, cutting 25–32 KB of document transfer does not move simulated FCP or LCP. The document finishes in parallel with the 79 KB render-blocking CSS. The +150 KB check shows the slope is real (5 ms/KB FCP, 6 ms/KB LCP, matching the lighthouse-analyst model) once the document becomes the long pole.
2. The robust effect is CPU. The document's parse and style long tasks disappear: TBT −100…150 ms mobile, main thread −250 ms. With JS, these tasks currently precede the simulated FCP, so they inflate FCP's CPU share instead of TBT. After boot-js lands, they enter the TBT window.
3. JS-side wins of HW-1, as an estimate: the 14.8 KB TickerStyles literal (entry) and the 10.9 KB slider literal (sliderVariants chunk) are about 6.5 KB gz of High-priority pre-LCP JS. At 5–6 ms/KB that is about −35 ms FCP/LCP mobile. Minified CSS adds about +6 KB gz render-blocking (est.), so net pre-LCP bytes are about −9 KB (HTML −8.5, JS −6.5, CSS +6).
