## 0. Bottom line

1. **The old harness measured the wrong document.** `measure-local.sh`/`measure-ab.sh` wait for readiness with bare `curl -sf "$UP$URLPATH"` (UA `curl/x` => `isbot()` true). That is the FIRST render of `/`, so the document cache (key `host::path`, `src/lib/http/documentCache.ts:196-224`, no bot/browser dimension) stores the **buffered bot variant** and Lighthouse gets it as HIT: **382 468 B / 14 `<script>`** vs the streaming browser variant **391 114 B / 22 `<script>`** (reproduced: `$SCRATCH/phase1/measurement/bot-warm.ts`, `warm-variants.ts`). Every `baseline2`/`measure-ab` number (and the server-cache/hydration reports built on it) is the bot variant. The same mechanism exists in production: whichever MISS comes first in a colo (Googlebot, `curl` monitoring) decides what browsers and PSI get for the freshness window. The production sample `psi/home.html` (15 scripts, one 18.6 KB react-query block) has the buffered shape.
2. **The old harness used HTTP/1.1 and a separate image origin; production is h2 on one origin.** Production LHR: 99/121 requests `h2` from the document origin, hero from `/media` same origin; local: `http/1.1` + `fixture.invalid` on its own origin. Lantern models these differently (`@paulirish/trace_engine/.../lantern/simulation/ConnectionPool.js`: h1 => `CONNECTIONS_PER_ORIGIN = 6` cloned connections, h2 => 1 connection; TLS adds a handshake RTT). Interleaved A/B, same artifact, 3+3 runs: **h2 vs h1 mobile LCP -0.30 s, desktop FCP -0.28 s, LCP -0.30 s, desktop perf 95 -> 98** (`ab-h1-h2.log`). The new harness serves document, assets AND fixture images from `https://fixture.invalid` over h2 (TLS, self-signed via `openssl`, Chrome `--host-resolver-rules` + `--ignore-certificate-errors`; verified Lighthouse accepts it).
3. **Noise floor (A/A, same artifact both sides, 3+3 interleaved, load 2-6 on 4 CPU): FCP/LCP mobile +-0.01 s, TBT mobile +464 ms (249 vs 713 ms), perf -13.** With the machine at load ~8, the same artifact gave TBT 4 762-5 529 ms (`baseline-h2.log`). Perf score on this host is a TBT lottery; FCP/LCP/SI/bytes are reliable at n=3, TBT needs n>=5 and A/B only.
4. **Simulated FCP mobile is bimodal on the same artifact (2.88-2.99 s vs 4.06-4.26 s; h1 also 5.0 s)**. Lantern `FirstContentfulPaint.getRenderBlockingNodeData` puts every High-priority script that finished before the observed FCP AND whose evaluation started before it into the FCP graph (`NetworkNode.hasRenderBlockingPriority`: `priority==='High' && Script`). All ~550 KB gzip boot/modulepreload JS is High; whether it is evaluated before the first unthrottled paint (CSS ends ~340 ms, chunks ~300-365 ms observed) is a race of tens of ms. Loser pays ~1.1 s of FCP on 1.6 Mb/s. PSI has the same race.
5. **`fetchpriority="low"` on `<link rel=modulepreload>` is ignored by Chrome 141** (what-if via proxy transform: all chunks still `High`, FCP/LCP delta 0.00 s) - so "make preloads low" cannot be done with the attribute; it needs preloads removed / deferred. What-if v2 (no modulepreload, entry `fetchpriority=low`): see §5.
6. **Document-weight gate implemented and green** on the fixture; production document measured with the same code (`--html`): 569 347 B HTML, 107 041 B `$tsr-stream-barrier`, 133 223 B inline CSS in 51 blocks, LCP image preloaded **6x** (5 in `<head>` + `Link`), 27 preload duplicates.
7. **Production `highPriorityBytesBeforeLcpImage` = 674.5 KB (mobile), fixture 618 KB** - the fixture reproduces the bandwidth-contention structure that drives LCP (EVIDENCE §10) within 10 %.
