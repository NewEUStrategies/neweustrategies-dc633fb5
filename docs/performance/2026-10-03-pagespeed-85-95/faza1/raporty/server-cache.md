2. **Document bytes ARE on Lantern's critical path**: every parser-discovered request depends on the full completion of the document node (`Simulator.js:171-173`, `PageDependencyGraph.js:126-150`). Production ships the document **gzip** (89 371 B transfer for 575 523 B, `lh/prod-mobile.json` network-requests) although Chrome offers br; brotli q9 of the same HTML = 57.3 KB, q11 = 52.2 KB (gzip-6 78.6 KB). Saving ~26 KB = ~0.14 s of mobile FCP/LCP/SI in Lantern (1.47 Mb/s). Link header (4 038 B, 33 entries) and 103 Early Hints give **zero** Lantern benefit (Link-initiated requests still hang off the root document node).
3. **Cold MISS = 4 serial DB waves before the shell, and above ~150-200 ms per round trip the homepage render degrades and is NOT stored.** Fixture trace (fresh process, 120 ms per PostgREST call): W1 settings+tokens+2 menus (104-258 ms) -> W2 `pages` + ads + `trending_posts` (230-377) -> W3 `get_entity_content` + `get_post_refs` (355-500) -> W4 5x `posts` for above-fold widgets (494-618) -> headers at 874 ms; W5 (newsletter + 3x posts) streams after the shell. **At 200 ms per call the same request returned `cache-control: private, no-store`, 162 748 B instead of 388 060 B (`[ssr-resilient] degraded render, seeded fallback for home.page`)** - the 600 ms home deadline (`src/lib/ssr/homeSsrBudget.ts:15`) lapsed in W3. The first visitor of a cold colo (PSI, Googlebot from the US) gets a degraded homepage; only the background degraded revalidation (2 tries / 10 min / isolate, `documentCache.server.ts:337-386`) stores a clean copy.
4. **`x-nes-cache-age` <= ~130 s on HIT is a tautology of the 3-minute cap**, not a symptom: HIT is by construction `age < freshMs <= 180 000 ms` (`documentCache.ts:47`, `documentCache.server.ts:829-834`), after which the entry is served STALE and re-rendered. The saved samples show 129 s (`psi/h1.txt`, 17:09:15) and 36 s (`faza1/server-cache/hb-1.txt`, 17:30:25) - not a constant band. What the cap really costs: one full render per key per ~3 min **per isolate generation** (L1 STALE re-renders without consulting a fresher L2, `documentCache.server.ts:835-842`), each with a chance to degrade.
5. **MISS TTFB 2.75-3.3 s vs `app;dur=942`**: the app accounts for < 1/3. The rest (1.8-2.4 s) is outside the handler: isolate cold start of a 13 MB worker (not measured - `server-init` only times the lazy import, `src/server.ts:241-244`), hosting/dispatch layer, and possibly body buffering by the hosting proxy. Not decidable from the sandbox; protocol in section 8.

## 3. Why MISS TTFB is 1.3-3.3 s

Production MISS sample: `ssr;dur=662, db;dur=2029;desc="n=23", edge-routing;dur=280, app;dur=942` (EVIDENCE section 2); `db` is the **sum** of anon round trips (`ssrTiming.ts` `SsrDbTiming.totalMs`), i.e. 88 ms average per call, 3x overlap. ## 4. Design to make MISS rare and fast

### 4a. Freshness: event-driven, not time-capped

- Today the 180 s cap exists only because purge cannot cross colos (`documentCache.ts:41-47`). Replace it with a **content version token**: `public.site_content_version(tenant_id, version bigint)` bumped by the existing purge path (`recordAudit`, `audit.server.ts:84`) and by the scheduler when a scheduled post goes live. Each isolate memoises the version and refreshes it **in the background** at most every 30 s (`runAfterResponse`, colo snapshot through `bootstrapCache.server.ts`), so the hot path never waits on it. Each entry records `contentVersion` at render. Lookup: same version and age < 6 h -> HIT; different version -> STALE (serve + revalidate). Keep `chromeDegraded` 30 s and add a hard cap (15-30 min) for time-dependent keys (ticker from `post_views`, ad emission windows).
- **Soft purge**: selective purge for `/`, `/blog`, post paths re-renders immediately (`documentRevalidator`, `src/server.ts:171-203`) under `waitUntil` instead of deleting, so the editor's colo (the Polish readers' colo) never has a post-publish MISS; full purge bumps and then re-renders the 4-8 top paths.
- **L1 STALE consults L2 first** (another isolate may have refreshed it) and a colo-wide best-effort lease (`cache.put` of a 30 s lease key) dedupes revalidations across isolates.

### 4c. Collapse the query waves

1. One-line, low risk: add `builder:`, `ad_placements:`, `ticker_posts:` to `EDGE_TTL_L2_KEY_PREFIXES` (`ssrCache.ts:65-72`). Cold isolate in a warm colo: 4 DB waves -> 0 for `/` (W1/W2 home keys are already L2).

Fully cold path: 4 waves -> 2 -> at 200 ms/call data ready at ~400 ms, inside the 600 ms deadline -> **clean and stored instead of degraded**.
3. Optional `chrome_bootstrap()` (audit item 2.1 leftover): settings + tokens + menus in one call (4 of the 6 Workers connections at t0 -> 1).
   Gates: `check:ssr-budgets` (`dehydrationWritesPerLoader` ceiling 11 on `__root.tsx` with zero slack), `check:loader-policy`, `check:rpc-contract`, `check:sql-*` for the RPC, `homeRoute.test.tsx`, `degradedRenderCachePipeline.test.ts`, SSR/hydration parity (the bundle must seed the **same** react-query keys).

### 4d. Warmers

- EU: `pg_cron` + `pg_net` already exist (`scheduler.yml:7-14`); a 60 s job `net.http_get` on `/`, `/en`, `/blog`, `/en/blog` warms the colo nearest the DB region (region unknown - audit 0.4). External multi-region monitor (EU-West near PSI's europe-west, EU-Central, US-East, US-Central) at 60-120 s with a real Chrome UA and `Accept-Language` pl/en.
- After deploy: poll `/api/public/version` until it changes, then warm all regions (Lovable publish has no hook in this repo).

### 4e. Bots and Lighthouse

Never bypassed (verified in code and in `faza1/server-cache/hb-*.txt` with the Lighthouse UA). Two caveats: (1) on a MISS `isbot` holds the first byte until `allReady` (W5 included); (2) if PSI's Chrome sends `Accept-Language: en-US` without the `lang` cookie, `/` answers `302 /en` (`src/start.ts:136-183`, `lib/i18n/langNegotiation.ts:66-91`), which Lantern charges as an extra request hop (RTT + origin latency, ~0.2-0.4 s mobile FCP/LCP). The saved local runs ended on `/` (laptop Chrome), PSI's final URL is unknown - verify in the PSI JSON (`finalDisplayedUrl`, `redirects`).

Targets: HIT ratio for `/` > 97 % (with L3: > 99 % from any colo), MISS TTFB < 800 ms (L3 read 0.05-0.3 s; fully cold render with 4c: ~0.7-0.9 s app), HIT TTFB < 200 ms (requires 4c-free path + item SC-8 below).

## 5. Browser Cache-Control, bfcache, cookies

- Browser sees `no-cache, must-revalidate, max-age=0` (hosting override). `no-cache` does **not** block bfcache (only `no-store` on the main resource does, and Chrome is relaxing even that); bfcache blockers to check belong to the client (open Supabase Realtime WebSocket, `unload` handlers) - LH's bf-cache audit is unscored.
- A short browser `max-age` (60 s, what the app already emits) or `stale-while-revalidate` is safe for anonymous readers (the document is the anonymous shell; session UI hydrates client-side; `sb-*`/`Authorization` already bypass). It has **zero** effect on PSI (cold profile) and requires the hosting to stop overwriting `Cache-Control` - not controllable from the repo.
- `set-cookie: __cf_bm` on every HTML response is Cloudflare Bot Management (30 min, `Domain=neweuropeanstrategies.com`), not the app. Effects: ~330 B per response; any future Cloudflare CDN caching of HTML would refuse responses with `Set-Cookie`; our key ignores non-`sb-*` cookies so it never causes a BYPASS.

## 8. Verification protocol (human, production)

1. **Classify any PSI run**: open the PSI JSON, read `audits["server-response-time"].numericValue` and `finalDisplayedUrl`. < 400 ms = HIT/STALE, > 1 000 ms = MISS/render. Compare `speed-index` vs `first-contentful-paint`: a MISS shows SI >> FCP on desktop.
2. **Batch**: 10 PSI API runs per form factor (with API key) at 10-minute intervals; HIT ratio = share with TTFB < 400 ms; target > 97 %.
3. **curl series** (`faza1/server-cache/series.sh`) extended with `cf-ray` colo, `x-nes-cache`, `x-nes-cache-age`, `server-timing`, `time_starttransfer` vs `time_total`, from the laptop (PRG/WAW) and from a US vantage (`workflow_dispatch` job on GitHub Actions).
4. **Body buffering test**: `curl -N -o /dev/null -w '%{time_starttransfer} %{time_total}' 'https://neweuropeanstrategies.com/?nesprobe=1'` (unknown param = BYPASS = fresh render): if starttransfer ~= total while `app;dur` << starttransfer, the hosting buffers the stream.
5. **Brotli**: `curl -sI -H 'accept-encoding: br' https://neweuropeanstrategies.com/ | grep -i content-encoding` before/after SC-7.
6. **Workers Logs** after SC-1: per-colo MISS share, `isoReq==1` share among MISS, `streamMs - appMs`, `degradedBy` histogram.
