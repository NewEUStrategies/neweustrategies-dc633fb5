# Verdict: lcp-path LP-2 (single source of truth for the preload)

Feasibility: WEAKENED (the mechanism holds, but the scope needs narrowing and two dependencies must be stated).
Effect: WEAKENED (the "~0 score" claim is right, but the byte numbers belong mostly to LP-1 and the gzip figure is overstated about 7x).

## Lens 1: feasibility in this codebase

What holds:

- React 19.2.0 (node_modules/react-dom/package.json:3), react-dom-server.edge.production.js:2149-2240 (pushImg). An `<img>` that is not lazy and not fp=low, has a srcSet and is not inside `<picture>` gets a preload keyed by `srcSet+"\n"+sizes`. With fp=high it always goes to highImagePreloads, which are flushed in the preamble before the stylesheets. The props come from the img itself, so the preload matches the img by construction.
- The app's own `imagePreloadLink` element (index.tsx:310-312, rendered by HeadContent) goes through the generic `<link>` branch, `pushLinkImpl(renderState.hoistableChunks, props)` at :1911. That branch does NOT dedupe against `imageResources`, so it is an extra element. Prod HTML (psi/home.html) confirms it: link@26362 (1853 B) has the same srcset and the same 25vw imageSizes as React's link@374. It is a byte-exact duplicate, and the browser makes no second request.
- OptimizedImage priority gives eager + fetchPriority=high, and the sizes have no "auto," prefix (atoms/OptimizedImage.tsx:121,125,130). Post covers in PostLayoutRenderer.tsx:231-238 and :287-294 use `priority`, so React preloads them.
- Gates: check:bundle, check:chunks and check:entry-purity are not touched (no new imports; index.tsx may stop importing imagePreloadLink). check:loader-policy (W1/W2/W4: cache policy, budgets, key parity) is not affected because the loader still does the same work. SSR/hydration parity: head() is computed from loaderData on both sides, so removing a link on both sides does not cause a mismatch. No CLS. No SEO or i18n effect (a preload is not an SEO signal).

What weakens it:

1. index.tsx has two coverPreload producers: latest-posts mode (:156-173) and builder (:236). head() (:310) cannot tell them apart, so loaderData needs a flag. homeRoute.test.tsx:603-611 asserts the head preload for the latest-posts first card. If LP-2 drops it for every mode, that test breaks, and so would the robustness the archive cards rely on.
2. Robustness regression in one real case: sectionStreaming.tsx:1-5. When the loader deadline is missed, a data-bound section (including the first fold) streams behind a server Suspense gate. React's auto-preload for an img inside that boundary is then flushed with the late segment, not in `<head>`. Today, a section 0 with a STATIC hero (image/static slider) plus a late data widget still gets the head link, because builderHeroPreload needs no cache for static items (heroImage.ts:89-97, 122-139). After LP-2 only the Link header covers that case. So keeping the Link header (index.tsx:255) is mandatory, not optional.
3. "Audit $.tsx and the other routes" goes beyond the files list. tag/category/blog.index/web-stories/events also append imagePreloadLink. ArchivePosts.tsx:52,75,96 prioritises only when `firstCardPriority && idx===0`, and head() cannot see that render-time decision. Dropping the head copy there removes the only in-HTML preload whenever priority is off. Restrict LP-2 to builder documents (index.tsx builder branch and $.tsx pages). Leave posts and archives as they are (one duplicate costs ~44 B gz).
4. Making React the single source amplifies LP-1's candidate rule. Whatever is eager gets preloaded, bypassing heroImage.ts's caution rules (light/dark pair :125-126, logo :130-136, A/B :263). lcpCandidate must keep those exclusions, and it must also skip hideOn.mobile. Today only hideOn.desktop is checked (:204). Otherwise the head preloads a widget mobile never paints.
5. The delegation needs a policy for "lcpCandidate picks a widget whose widgetPreload returns null" (data cache empty, unsupported post-list variant). builderHeroPreload must then return null, NOT fall through to the next DOM-order widget. Falling through re-creates F4, because that widget is lazy after LP-1.

Better mechanism with the same intent and more robustness: call `preload(href, {as:"image", imageSrcSet, imageSizes, fetchPriority:"high"})` from react-dom in the route component (shell), using loaderData.coverPreload. The float `preload()` (react-dom-server.edge.production.js:2972-3012) writes the SAME `imageResources[srcSet\nsizes]` key that pushImg checks (:2190). React then emits exactly one high preload in the preamble, even when the hero section streams later, and the img's own auto-preload is skipped. That gives 0 duplicates without depending on where the img renders. Alternatively, keep the head link and just fix the candidate: the duplicate costs 44 B gz.

## Lens 2: effect realism

- LP-2's own head change removes ONE link: 1853 B raw, 44 B gzip-9 (computed by deleting link@26362 from psi/home.html). Its srcset repeats link@374 within the 32 KB deflate window. At 1.6 Mb/s that is 0.2 ms, so 0 in Lantern. The "4 duplicate links / ~7 KB raw / ~1 KB gz" combine LP-1 and LP-2: removing 4 of the 5 head image preloads (keeping the hero's) is 7074 B raw but only 144 B gz, not ~1 KB. The 3 React duplicates disappear only because LP-1 makes their imgs lazy.
- The "desktop 25vw->480w mis-preload" costs nothing today. The 480w is also requested by React's preload of the eager cards (link@374), and those cards are painted. prod-desktop.json shows the 480w and the 768w (LCP) both High from 3405 ms, so it does not delay the hero. LP-2's real value is conditional: after LP-1 makes the cards lazy, an unchanged builderHeroPreload would leave an orphan 25vw head link plus a Link header, i.e. +15.8 KB High pre-LCP on desktop. At ~10 Mb/s simulated desktop throughput that is about 13 ms, or about 0.01 s LCP, so < 0.1 pt. On mobile the 25vw sizes resolve to 100vw, the same 768w URL as the hero, so 0.
- Lantern does not separate a head preload from a Link-header preload of the same URL (one network record, initiated by the document). So moving the preload source changes no graph edge.

Corrected estimate: 0 score points on both form factors, today and after LP-1. HTML −1.85 KB raw / −44 B gz (LP-2 alone), or −7.1 KB raw / −144 B gz together with LP-1. It prevents about −0.01 s desktop LCP of orphan-preload regression that LP-1 alone would introduce. Its value is correctness and durability (preload == painted candidate), not score.
