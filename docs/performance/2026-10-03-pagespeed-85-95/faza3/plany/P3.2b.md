1. **Jeden plik zamiast dwóch: wykonalne bez kompromisu wizualnego.** Podzbiór Red Hat Display 1.030 (latin +

   (`src/styles.css:87-94`) jest policzony poprawnie dla wagi 400, ale tytuły kart, które się przesunęły,
   **w ogóle go nie używają**: CMS (`site_settings.theme_design`) zapisuje dla `postTitle`/`postExcerpt` stary stos
   `"Red Hat Display", system-ui, -apple-system, Segoe UI, sans-serif` (bez fallbacku), a

   załadowania fontu tytuły (waga 600) renderują się systemowym `DejaVu Sans Bold`, który jest o ~27% szerszy niż
   RHD 600, więc tytuły zawijają się o linię więcej, a po podmianie karty kurczą się o 17–27 px (ślad desktop-3,
   §2). Ten sam stary stos jest w fixture (`e2e/fixtures/first-visit.json`, `settings[11].value.postTitle`), więc
   błąd da się odtworzyć lokalnie.
3. **Drugi, mniejszy mechanizm: jedna twarz fallbacku dla wszystkich wag.** Dla wag 600–900 Chrome syntetyzuje
   pogrubienie z Arial/Liberation Regular przy `size-adjust` policzonym dla wagi 400. Fallback jest wtedy o 5–12%
   węższy niż RHD w danej wadze (ticker: przesunięcie 5 px w poziomie, 0,0014 w desktop-2). Lek: sześć twarzy
   fallbacku z zakresami `font-weight`, prawdziwy Bold (`local("Arial Bold")` itd.) dla wag ≥ 550 i `size-adjust`
   / `ascent-override` / `descent-override` policzone osobno dla każdej wagi z prawdziwych plików (tabela w §6).
4. Zakres plików z `PLAN-FALI-3.md` §P3.2b (`styles.css`, `fontPreload.ts`, `rootHead.ts`, `src/assets/fonts/*`,
   test) **nie wystarcza do celu CLS = 0**. Trzeba go rozszerzyć o `src/lib/theme/themeDesign.ts` (normalizacja stosu
   przy emisji CSS) oraz o `src/routes/__root.tsx` (dwa importy `?url` i obiekt `ROOT_ASSETS`, rozłączne z regionami

## 4. Krok A: wygenerowanie podzbioru offline (poza repo, bez nowej zależności)

Źródło: pełny zmienny font z repozytorium Google Fonts (ta sama wersja 1.030, co dzisiejsze pliki; potwierdzone
tabelą `name` i identycznymi metrykami). GitHub jest w tym środowisku zablokowany, mirror jsDelivr działa:

```bash
W=$SCRATCH/p32b            # katalog roboczy POZA repo
mkdir -p $W/dl && cd $W/dl # pobrany plik = dane niezaufane, osobny katalog
curl -sSL -o RHD-gf.ttf \
  "https://cdn.jsdelivr.net/gh/google/fonts@main/ofl/redhatdisplay/RedHatDisplay%5Bwght%5D.ttf"
sha256sum RHD-gf.ttf       # 46c9d4c4a2415e7e72020b318f5cda2bcbc9018d78b1a67e480a76d8d6e4b379 (98 360 B)
python3 -m venv $W/venv && $W/venv/bin/pip install fonttools==4.66.1 brotli==1.2.0 uharfbuzz==0.56.3
```

Generowanie (fonttools `pyftsubset`; zachowuje `fvar/gvar/HVAR/MVAR/avar/STAT`, czyli oś wag):

```bash
U="U+000D,U+0020-007E,U+00A0-00FF,U+0131,U+0152-0153,U+02BB-02BC,U+02C6,U+02DA,U+02DC,\
U+0300-0301,U+0303-0304,U+0308,U+2000-206F,U+20AC,U+2122,U+2191,U+2193,U+2212,U+2215,U+FEFF,U+FFFD,\
U+0104-0107,U+0118-0119,U+0141-0144,U+015A-015B,U+0179-017C"

cd $W/out && $W/venv/bin/pyftsubset $W/dl/RHD-gf.ttf --unicodes="$U" --layout-features="$F" \
  --flavor=woff2 --output-file=red-hat-display-latin-pl.woff2
# wynik: 31 100 B, sha256 ca7035aef3b146e7a8d1023a5866bba1313bd011cdb541c5bcfbd6ef74ede0bf
# (dwa kolejne przebiegi dały ten sam hash)
cp red-hat-display-latin-pl.woff2 /home/user/neweustrategies-dc633fb5/src/assets/fonts/
```

### 6.1 Metoda (do raportu i komentarza w CSS)

- `size-adjust(w)` = szerokość tekstu w RHD w wadze `w` / szerokość tego samego tekstu w fallbacku (Liberation Sans
  Regular dla w ≤ 500, Liberation Sans Bold dla w ≥ 600; Liberation = metrycznie identyczny z Arialem, Arimo to ten
  sam projekt). Szerokości z kształtowania HarfBuzz (kerning włączony, jak w Chrome) na korpusie: widoczny tekst
  produkcyjnej strony `/` (`$SCRATCH/w3/prod/d2.html`, tytuły i zajawki) + wartości słownika `src/lib/locale/pl.ts`;
  razem 49 385 znaków. Skrypt: `$SCRATCH/p32b/overrides.py <nowy-font> $SCRATCH/p32b/corpus-home-pl.txt`.
- `ascent-override = hhea.ascender / upm / size-adjust` = 101,8% / sa; `descent-override` = 30,5% / sa;
  `line-gap-override: 0%` (hhea.lineGap = 0). Iloczyn `override × size-adjust` = metryka RHD, więc wysokość linii
  przy `line-height: normal` i położenie linii bazowej są identyczne w fallbacku i w RHD w KAŻDEJ wadze.
- Wrażliwość na korpus: dla samej strony `/` wartości są niższe o 0,1–0,8 pp, dla samego słownika PL o 0,1 pp, dla
  słownika EN wyższe o 0,1–0,7 pp. Wybrany korpus łączony to kompromis PL; błąd ±1% szerokości w porównaniu z ~27%
  (system-ui) i 5–12% (jedna twarz) dziś.

## 7. Krok D: normalizacja stosu Theme Design (`src/lib/theme/themeDesign.ts`)

Nowa eksportowana funkcja (w tym samym module, żeby nie tworzyć chunku ani nie dotykać domknięcia bootu):

```ts
// Stos z CMS sprzed wprowadzenia fallbacku metrycznego ("Red Hat Display", system-ui, …)
// spadał do system-ui do czasu fontu: inna szerokość = inne łamanie = CLS przy podmianie.
const RHD_FAMILY = /(^|,)(\s*)(["']?)Red Hat Display\3(?=\s*(?:,|$))/i;
const RHD_FALLBACK = /(["']?)Red Hat Display Fallback\1/i;
export function withRedHatDisplayFallback(stack: string): string {
  if (RHD_FALLBACK.test(stack) || !RHD_FAMILY.test(stack)) return stack;
  return stack.replace(RHD_FAMILY, (m) => `${m}, "Red Hat Display Fallback"`);
}
```

Użycie: `themeDesign.ts:615` → `--td-pt-family:${withRedHatDisplayFallback(t.postTitle.fontFamily)};`,
`:622` → to samo dla `postExcerpt`. Nie normalizować w `themeDesignFromRaw` (`:383`): panel ma pokazywać i zapisywać
to, co wybrał administrator. `themeDesignToStyleVars` (`:653`) parsuje wyjście `themeDesignToCss`, więc podgląd na
żywo dostaje to samo za darmo. Hash bloku liczony z wejścia (`useDeferredStyleCss.ts:46`), więc hydratacja nie
regeneruje bloku. Generator nie jest w domknięciu bootu (§1), więc `bootClosureGzipBytes` bez zmian.

Test (`themeDesignFontStack.test.ts`): stary stos produkcyjny → fallback wstawiony zaraz po RHD; stos domyślny (z
fallbackiem) bez zmian; `Inter, system-ui, sans-serif` bez zmian; `'Red Hat Display', serif` (apostrofy) →
fallback; `Red Hat Display Fallback` sam → bez zmian; `"Red Hat Display Pro"` → bez zmian; idempotencja
(`f(f(x)) === f(x)`); `themeDesignToCss(themeDesignFromRaw({postTitle:{fontFamily: STARY}}))` zawiera
`--td-pt-family:"Red Hat Display", "Red Hat Display Fallback", system-ui`.

Alternatywa danych (decyzja właściciela, nie zamiast kodu): jednorazowa aktualizacja wiersza

   (dosłowne „oś wag zachowana”); zgoda = podmiana pliku i stałej w teście §9.2 pkt 4 (`min ≤ 400`).
2. Czy jednorazowo poprawić w CMS wiersz `theme_design` (postTitle/postExcerpt `fontFamily`) na stos z fallbackiem?
   Kod z §7 działa niezależnie; poprawka danych tylko porządkuje panel.

## 15. Odrzucone warianty

- **Zostawić jedną twarz fallbacku i tylko przeliczyć `size-adjust`:** nie rusza przyczyny (stos CMS bez
  fallbacku), a jedna wartość nie pasuje do wag 400–900 (rozrzut 93,4–100,6%).
- **Lokalny `@font-face` w rodzinie „Red Hat Display” jako łatka na stosy bez fallbacku:** twarz `local()` jest
  zawsze „załadowana”, więc przeglądarka nigdy nie podmieni jej na woff2 dla pokrytych znaków.
- **`font-display: optional`:** usuwa podmianę, ale przy wolnej sieci strona zostaje w Arialu do następnej wizyty
  (marka); poza decyzją właściciela.
- **Scalanie dzisiejszych `latin` + `latin-ext` przez `fontTools.merge`:** nie obsługuje fontów zmiennych (`gvar`).
- **Podzbiór przez Google Fonts API (`text=`):** traci cechy OpenType i kontrolę wersji.
