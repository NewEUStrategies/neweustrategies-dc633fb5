# Ocena systemu SSR — architektura, cache, data-fetching, bundle

**Data:** 2026-07-24 · **Zakres:** cały potok SSR (middleware → cache dokumentów → loadery → render → hydratacja) ·
**Metoda:** analiza kodu (`plik:linia`), realny build produkcyjny zmierzony na tej sesji (`vite build`, Nitro `cloudflare-module`), audyt data-fetchingu wszystkich publicznych tras z loaderami.
**Skala ocen:** 0–10, przyznawana surowo (punkt odniesienia: dojrzała komercyjna platforma wydawnicza).

---

## Werdykt ogólny: **5,9 / 10** — bardzo dobre fundamenty, systemowo dziurawe pokrycie

Architektura SSR jest przemyślana i bezpieczna (anonimowa skorupa, tenant-scoping „by construction",
fail-safe middleware, single-flight SWR), ale **dwie systemowe luki niweczą większość jej potencjału**:

1. **Cache dokumentów obejmuje 3 z 23 publicznych tras z loaderami.** `documentStorePolicy`
   (`src/lib/http/documentCache.ts:159-174`) zapisuje dokument tylko, gdy odpowiedź niesie
   `public` + `s-maxage>0` — a ten nagłówek ustawiają wyłącznie `index.tsx`, `$.tsx` i `sitemap.tsx`.
   **Kategorie, tagi, blog, autorzy, podcasty, programy, eksperci, tracker, web-stories, pricing —
   20 tras — renderują się od zera z kompletem zapytań do bazy na KAŻDE żądanie**, bez cache
   edge'owego, CDN-owego i przeglądarkowego.
2. **Cały cache żyje w pamięci pojedynczego izolatu Cloudflare.** Izolatów jest wiele, żyją krótko,
   każdy grzeje się osobno, a purge przy publikacji czyści tylko ten, który obsłużył mutację
   (`documentCache.server.ts:288-321`). Realny hit-rate na rozproszonym ruchu jest ułamkiem tego,
   co dawałby cache per-colo (Cloudflare Cache API) — dostępny w runtime bez żadnych bindingów.

Do tego dochodzi najcięższa publiczna trasa (`author.$slug` — **~22 round-tripy do Supabase na
żądanie, w 4–5 sekwencyjnych falach, bez żadnego cache**) oraz 21-megabajtowy (nieminifikowany)
bundel serwera z echarts, edytorami admina i ajv w grafie SSR.

| Obszar                                       | Ocena   | Uzasadnienie skrótowe                                                                       |
| -------------------------------------------- | ------- | ------------------------------------------------------------------------------------------- |
| Poprawność i bezpieczeństwo architektury SSR | **8,5** | anonimowa skorupa + gating RPC, tenant-scoping kluczy, fail-safe middleware                 |
| Render i streaming                           | **7,5** | streaming + Suspense poniżej foldu, LCP preload, View Transitions                           |
| Cache dokumentów (konstrukcja)               | **7,0** | single-flight SWR, stale-as-bezpiecznik, tee strumienia, budżety bajtów                     |
| Cache dokumentów (skuteczność systemowa)     | **4,0** | pokrycie 3/23 tras, per-isolate, purge jednego izolatu                                      |
| Data-fetching loaderów SSR                   | **5,0** | wpis dobrze zrównoleglony; archiwa sekwencyjne z N+1; autor ~22 RT                          |
| Bundel serwera / cold start                  | **4,5** | 21 MB raw (`minify:false`), echarts/edytory/ajv w SSR, router-chunk 1,55 MB eager           |
| Bundel klienta / hydratacja                  | **5,0** | budżety CI przekroczone: public 1541 KB gzip, entry 377 KB gzip                             |
| Obserwowalność SSR                           | **6,0** | RUM (TTFB/LCP/CLS/INP) + karta cache; brak czasu renderu/DB per trasa, snapshot per-isolate |

Po wdrożeniu rekomendacji z Fazy 1–2 realny pułap systemu to **~8/10** — konstrukcja już na to pozwala.

## 1. Jak działa system dziś (stan faktyczny)

### 1.1 Potok żądania

```
Request
  → securityHeadersMiddleware        (HSTS/CSP/nosniff — czyste, bez DB)      start.ts:100
  → seo404Middleware                 (fire-and-forget log 404 do DB)          start.ts:138
  → redirectMiddleware               (index reguł per tenant, cache 30 s)     start.ts:114
  → legacyLangQueryMiddleware        (kanonizacja ?lang= → /en)               start.ts:15
  → documentCacheMiddleware          („NES Edge Cache", per-isolate)          start.ts:218-224
      HIT   → replay z pamięci (0 SSR, 0 DB)
      STALE → replay + single-flight rewalidacja w tle
      MISS  → router → root loader → route loader → streaming render
              → tee strumienia do magazynu (jeśli polityka pozwala)
```

- Rezolucja tenanta: katalog hostów cache'owany 60 s per isolate (`tenant.server.ts:44`), reguły
  redirectów 30 s (`redirects.server.ts:43`) — w stanie ustalonym middleware nie dokłada round-tripów. ✓
- Wszystkie zapytania SSR idą **bezpośrednim klientem `supabase-js` do PostgREST po HTTPS**
  (`integrations/supabase/client.ts` + `tenant-host-fetch.ts`); każda „fala" `Promise.all` ≈ 1 RTT
  worker→Supabase. Loadery publicznych tras nie używają `createServerFn`.

### 1.2 Root loader — koszt stały każdego renderu (`__root.tsx:196-277`)

Na każdy nie-cache'owany dokument: `syncI18nToRequest` + **4 zapytania** (`site_settings`,
`site_design_tokens` ×2 — patrz §3.4, `post_layout_settings`) + dla stron z chrome: ticker
i prefetch dokumentów buildera header+footer (budżet 2×2500 ms, `__root.tsx:263-268`).
Tylko `site_settings`, menu i ticker są za `edgeTtlCache` 60 s; **design tokens, global colors
i post-layout biją do bazy przy każdym renderze**.

### 1.3 Warstwy cache

| Warstwa                    | Zasięg                                | TTL                         | Pokrycie                                                                                       |
| -------------------------- | ------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------- |
| NES Edge Cache (HTML)      | **per-isolate**, 24 MB, wpis ≤1 MB    | fresh ≤180 s, SWR ≤6 h      | tylko trasy z `contentCacheControl()`: **3/23**                                                |
| `edgeTtlCache` (zapytania) | **per-isolate**, 500 wpisów           | per wywołanie (60 s typowo) | settings, menu, ticker, home, SEO/feedy — **bez** resolvedContent/archiwów/autora              |
| react-query `QueryClient`  | request-scoped                        | n/d                         | dedupe wyłącznie w obrębie jednego renderu                                                     |
| CDN / przeglądarka         | `max-age=60, s-maxage=900, swr=86400` | —                           | te same 3 trasy; **Cloudflare domyślnie nie cache'uje HTML**, więc `s-maxage` jest dziś martwe |

### 1.4 Co jest zrobione dobrze (i czego nie ruszać)

- **Anonimowa skorupa SSR + gating po hydratacji** (`get_entity_content`, `lib/access/gating.ts`) —
  dokument identyczny dla gościa i zalogowanego ⇒ współdzielenie cache jest bezpieczne, paywall
  nie wycieka treści. To fundament całej strategii i jest poprawny.
- **Język w ścieżce URL** (PL goła, EN `/en`) — cache per język bez `Vary`, bez cookie-poisoningu
  (`router.tsx:78-89`).
- **Single-flight SWR + „stale zamiast 500"** przy awarii renderu (`documentCache.server.ts:246-265`).
- **Tenant-scoping kluczy cache „by construction"** (`ssrCache.ts:36-37`, `documentCache.ts:141-142`).
- **Middleware fail-safe** — żaden DB-touch nie może położyć łańcucha SSR (`start.ts:214-217`).
- Streaming below-the-fold przez Suspense (`$.tsx:207-210`), preload okładki LCP w `head()`,
  self-hostowane fonty z preloadem subsetu, Speculation Rules, `dns-prefetch`/`preconnect` do Supabase.
- Świadomie wyczyszczone wcześniejsze N+1 (autorzy wpisu `public.ts:518-526`, blog list `public.ts:412-415`).
- CI: budżety bundla (`check-bundle-size.ts`), acykliczność chunków (`check-chunk-graph.ts`), RUM Web Vitals.

## 2. Ustalenia krytyczne (P0)

### P0-A · 20 z 23 publicznych tras bez `Cache-Control` ⇒ zero cache na całej powierzchni archiwów

`grep setCacheControlHeader|contentCacheControl src/routes/` → tylko `index.tsx`, `$.tsx`, `sitemap.tsx`.
Trasy **bez** nagłówka (pełny SSR + komplet zapytań DB na każde żądanie, również od botów):
`category.$slug`, `tag.$slug`, `blog.index`, `author.$slug`, `experts`, `contribute`, `cookies`,
`live`, `podcast.$slug`, `podcasts.$show`, `podcasts.index`, `pricing`, `programs.$slug`,
`programs.index`, `tracker.$slug`, `web-stories.$slug`, `web-stories.index`…

Skutek podwójny, bo `documentStorePolicy` (`documentCache.ts:159-174`) traktuje brak
`public + s-maxage` jako „nie zapisuj" — **NES Edge Cache jest dla tych tras wyłączony z definicji**,
a przeglądarka też nic nie trzyma (brak nagłówka = heurystyki).

**Rekomendacja (systemowa, nie per-trasa):** domyślna polityka w potoku zamiast 20 wywołań
w loaderach — middleware tuż nad `documentCacheMiddleware`: GET + `text/html` + status 200 +
ścieżka poza `PUBLIC_DOCUMENT_DENY_PREFIXES` (lista już istnieje i jest współdzielona,
`documentCache.ts:50-66`) + **brak** już ustawionego `cache-control` ⇒ `contentCacheControl()`.
Trasa zachowuje prawo nadpisania (preview/personalized emitują `private, no-store` jak dotąd).
Wyjątek do rozważenia: `/live` (live blog) — krótszy `s-maxage` (np. 30 s) zamiast wykluczenia.

**Efekt:** archiwa i strony autorskie przechodzą z „pełny render + 5–22 zapytań DB za każdym razem"
na HIT/STALE z pamięci (mikrosekundy) w oknie świeżości; boty (największy ruch na archiwach)
przestają młócić Supabase.

### P0-B · Cache wyłącznie per-isolate — brak Cloudflare Cache API (per-colo)

Świadomy kompromis opisany w `documentCache.server.ts:18-21`, ale jego koszt rośnie z ruchem:
izolaty workerd są mnożone i ubijane poza kontrolą aplikacji; każdy zaczyna z zimnym magazynem;
`purgeDocumentCache` czyści wyłącznie bieżący isolate (`documentCache.server.ts:288-306`), reszta
dogania dopiero po ≤3 min. Karta `/admin/performance?tab=cache` pokazuje statystyki **jednego
losowego izolatu** (`edgeCache.functions.ts:22-23`), więc raportowany hit-rate nie opisuje systemu.

W kodzie nie ma ani jednego użycia `caches.default` / KV / `waitUntil` (grep pusty) — a Cache API
jest dostępne w każdym Workerze bez bindingów i bez zmian w deployu.

**Rekomendacja — dwupoziomowy cache dokumentów:**

- **L1** (bez zmian): obecna mapa in-memory — chroni przed stampede w obrębie izolatu, koszt ~0.
- **L2**: `caches.default` (per-colo, współdzielony między izolatami kolonii) — `match()` przy MISS
  L1, `put()` przy store (z `waitUntil`, patrz P2-D). Klucz: syntetyczny URL
  `https://<host>/<wersja-treści><pathname>?<keyedParams>`.
- **Purge bez purge'a**: klucz wersjonowany. Licznik wersji treści tenanta (bump przy
  publish/update/delete — dokładnie tam, gdzie dziś woła się `purgeDocumentCacheForCurrentHost`,
  `audit.server.ts`) trzymany w L1 z krótkim TTL; zmiana wersji unieważnia całe L2 bez iterowania
  kluczy. Endpoint `/api/public/version` już istnieje jako wzorzec (`lib/cacheBusting.ts:70`).
- Zachować obecny kontrakt BYPASS (auth/cookie `sb-*`, deny-lista, keyed params —
  `documentCache.ts:114-143`) — jest poprawny i przetestowany.

**Efekt:** hit-rate rośnie z „per-isolate" do „per-colo" (dla ruchu z jednego kraju ≈ jedna–dwie
kolonie ⇒ większość żądań trafia w cache), publikacja widoczna natychmiast w całej kolonii,
statystyki przestają być loterią izolatu.

### P0-C · `author.$slug` — ~22 round-tripy w 4–5 sekwencyjnych falach, bez żadnego cache

`expertHubQueryOptions` (`lib/experts/queries.ts:149-288`): profil → `Promise.all` ×10 (w tym
**4 pełne, niefiltrowane tabele taksonomii**: `programs`, `regions`, `categories`, `tags` —
`queries.ts:227-232`, tylko do faset UI) → `fetchMaterials` w **3 kolejnych falach**
(`queries.ts:31-115`, do 11 zapytań) → sekwencyjnie doklejony layout
(`author.$slug.tsx:59-63`). Brak `edgeTtlCache`, brak `Cache-Control` (P0-A).

**Rekomendacja:** (1) natychmiast: objąć P0-A + `edgeTtlCache(60 s)` na całość huba;
(2) docelowo: **jeden RPC SQL** (`get_expert_hub(slug)`) zwracający hub jako JSON — z ~22 RT
do 1–2 RT; fasety liczyć w SQL zamiast ściągać 4 tabele; (3) minimum pośrednie: sparować fale
`fetchMaterials` (A+B da się złączyć po przepisaniu na `.in()` z id z fali A) i zrównoleglić layout.

## 3. Ustalenia wysokie (P1)

### P1-A · Archiwa kategoria/tag: sekwencyjny łańcuch + N+1 na `page_full_path`

`taxonomyArchiveQueryOptions` (`lib/queries/archives.ts:87-205`): `categories` → pivot →
`featured_section` → `posts(count)` → `hydrateHref`, gdzie `hydrateHref` (`archives.ts:23-37`)
woła RPC `page_full_path` **per unikalny `parent_page_id`** (równolegle, ale do ~60 wywołań).
**Fix:** `featured_section` równolegle z pivotem; batch-RPC `page_full_paths(uuid[])` (albo
zmaterializowana kolumna `full_path` na `pages`) zamiast N wywołań; docelowo `edgeTtlCache(60 s)`.

### P1-B · Render wpisu bez cache zapytań — każdy MISS dokumentu to ~10 RT

`resolvedContentQueryOptions` (`lib/queries/public.ts:460-620`) jest wzorowo zrównoleglony
(3 fale: `resolve_path` → `Promise.all` ×7 → `Promise.all` ×2), ale nie ma `edgeTtlCache`, więc
po każdej eksmisji/rotacji izolatu wpis płaci pełne ~10 RT. **Fix:** `edgeTtlCache(30–60 s,
klucz per segments+lang)` — treść i tak ma okno świeżości 3 min w cache dokumentów; alternatywnie
konsolidacja przez PostgREST embedding (`posts?select=...,post_tags(tags(...)),post_categories(...)`)
zbije fale 2–3 do jednej.

### P1-C · Root loader: dwa zapytania do tego samego wiersza + trzy zapytania bez TTL

`designTokensQueryOptions` (`lib/builder/designTokens.ts:55`) i `globalColorsQueryOptions`
(`hooks/useGlobalColors.ts:18`) czytają **ten sam wiersz `site_design_tokens`** dwoma round-tripami
na każdej trasie (`__root.tsx:213-216`); razem z `postLayoutSettingsQueryOptions` to 3 zapytania
poza `edgeTtlCache`. **Fix:** jeden select z oboma zestawami kolumn + `edgeTtlCache(60 s)` na
wszystkie trzy — zdejmuje 3 RT z każdego nie-cache'owanego renderu.

### P1-D · Slider manualny: 2 sekwencyjne RT per slajd + ciężka tabela `profiles`

`postRefQueryOptions` (`lib/builder/contentRefs.ts:100-113`): `fetchPostRef` → await →
`fetchAuthorInfo`, per referowany wpis (`builder/prefetch.ts:148`); `fetchAuthorInfo` czyta
`profiles` zamiast `profiles_public` (`contentRefs.ts:66`). **Fix:** jedno zapytanie z embeddingiem
autora, widok `profiles_public`, batch po wszystkich `postId` slidera.

### P1-E · Strona główna: potrójny odczyt `site_settings[reading]`

`home-mode` (`public.ts:294-302`) i `home-page` (`public.ts:313-317`) czytają osobno wiersz,
który root loader ma już w ciepłej mapie bulk. **Fix:** przekazać ustawienia z mapy (lub scalić
oba klucze w jeden fetch za `edgeTtlCache`).

### P1-F · Redirect 301 na `post.$slug` — 2 sekwencyjne RT bez cache

`post.$slug.tsx:11-30`: select `posts` → RPC `page_full_path`, poza react-query i `edgeTtlCache`,
na każdy hit starego formatu linku (w tym boty z indeksu). **Fix:** `edgeTtlCache(300 s)` po slugu.

## 4. Ustalenia średnie (P2) — bundel, cold start, obserwowalność

### P2-A · Bundel serwera: 21 MB raw / ~4,0 MB gzip, 769 modułów, `minify:false`

Zmierzone na tej sesji (`.output/server`). Największe pozycje w grafie SSR:

| Moduł                                                      | Rozmiar (raw)              | Uwaga                                                                          |
| ---------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------ |
| `_ssr/router-*.mjs`                                        | **1 548 kB** (357 kB gzip) | route tree + configi wszystkich tras — **ładowany eager na cold start**        |
| `_libs/echarts.mjs` + `zrender`                            | **1 536 + 407 kB**         | wykresy canvas — **nie renderują się w SSR**, a są w grafie serwera            |
| `_ssr/Builder-*.mjs`                                       | 763 kB                     | edytor wizualny (admin ma `ssr:false`, `admin.tsx:10` — moduł i tak w deployu) |
| `_ssr/lucideIconNodes.generated`                           | 534 kB                     | pełna mapa ikon                                                                |
| `_libs/react-dom.mjs`                                      | 499 kB                     | —                                                                              |
| `_libs/ajv.mjs` + MCP SDK                                  | 423 + 176 kB               | zaciągane przez `routes/mcp.ts`                                                |
| `_ssr/PostBlockEditor` / `ThemeOptionsPane` / `ChatWindow` | 417 / 290 / 238 kB         | powierzchnie admina w bundlu SSR                                               |

`minify:false` obejmuje serwer celowo (OOM przy `build:dev`, `vite.config.ts:29-40`), ale kosztem
~2–3× większego parse'a na cold starcie izolatu i większego artefaktu deployu.
**Fix:** (1) spróbować `minify:"esbuild"` wyłącznie dla środowiska SSR w pełnym buildzie
(OOM raportowano przy `build:dev`; esbuild-minify jest tani pamięciowo — zweryfikować na CI);
(2) wyciąć echarts z grafu SSR (`ClientOnly`/dynamic import w widgetach wykresów);
(3) lazy-import MCP SDK w handlerze `mcp.ts`; (4) rozważyć odchudzenie eager route-configów
(`head()`/`validateSearch` tras admina) z router-chunka.

### P2-B · Bundel klienta: budżety CI przekroczone (hydratacja drożeje)

Zmierzone: **public 1540,9 KB gzip** (budżet 1475), **overall 2607,0 KB** (2518), **największy
chunk = entry `index-*.js` 377,0 KB gzip** (budżet 350) — `bun run check:bundle` kończy się błędem
na czystym branchu. Na content-site entry ~380 KB gzip to realny koszt TTI/INP po każdym SSR.
**Fix:** wrócić do zielonych budżetów planem z `check-bundle-size.ts:40-60` (wydzielenie
`@tanstack` z entry, odchudzenie eager-zestawu widgetów chrome); atrybucję bajtów robić
`vite.measure.config.ts`. Długoterminowy cel z komentarzy repo (~250 KB public) podtrzymać.

### P2-C · Brak metryk czasu renderu SSR

`Server-Timing` niesie dziś tylko status cache (`documentCache.server.ts:119`). RUM zbiera TTFB
po stronie klienta, ale nie da się rozłożyć MISS-a na „czas DB vs czas renderu" per trasa.
**Fix:** zmierzyć w `documentCacheMiddleware` czas `next()` i emitować
`server-timing: ssr;dur=…` obok statusu; opcjonalnie licznik RT do Supabase per żądanie
(wrapper na `fetchWithTenantHost`) jako `db;desc="n=12";dur=…`. Wpina się w istniejący RUM
(przeglądarka wystawia Server-Timing w `PerformanceResourceTiming`).

### P2-D · Praca po odpowiedzi bez `waitUntil`

`collectStream` do magazynu (`documentCache.server.ts:193`, komentarz wprost: „runtime utnie
zbieranie") i log 404 (`start.ts:142`) wiszą na `void promise` — workerd może je ubić po
domknięciu odpowiedzi, co zaniża store-rate cache. **Fix:** `event.waitUntil` (h3/nitro udostępnia
kontekst wykonawczy CF) dla obu miejsc.

### P2-E · Chrome warm-up ×2 na każdej trasie z budżetem 2×2500 ms

`__root.tsx:263-268` grzeje dokumenty buildera header i footer osobno; bogaty footer z widgetami
post-list/slider to kilkanaście RT (`builder/prefetch.ts:115-153`) na każdym nie-cache'owanym
renderze. Po wdrożeniu P0-A/P0-B koszt amortyzuje się cache'em dokumentów; niezależnie warto
objąć wynik `prefetchCachedRouteQueries` dla chrome `edgeTtlCache(60 s)` (dokumenty header/footer
zmieniają się rzadko).

## 5. Plan wdrożenia (sekwencja świadomie od najtańszych zysków)

### Faza 1 — tydzień 1 (quick wins, samo TS, bez zmian infrastruktury)

1. **[P0-A]** Middleware domyślnego `Cache-Control` dla publicznych dokumentów (deny-lista już
   istnieje). Wyjątek `/live` → krótkie TTL. _Efekt: NES Edge Cache i przeglądarka zaczynają
   działać na ~20 trasach._
2. **[P1-C]** Scalone zapytanie `site_design_tokens` + `edgeTtlCache` na trzech query root loadera.
3. **[P1-B]** `edgeTtlCache` na `resolvedContent`; **[P0-C cz.1]** `edgeTtlCache` na `expertHub`;
   **[P1-A cz.1]** `featured_section` równolegle; **[P1-E]**, **[P1-F]**.
4. **[P2-C]** `Server-Timing: ssr;dur` — od pierwszego dnia mierzy efekty pozostałych faz.

### Faza 2 — tydzień 2–3 (fundament: cache per-colo + SQL)

5. **[P0-B]** L2 na `caches.default` z kluczem wersjonowanym + `waitUntil` (**[P2-D]**).
6. **[P0-C cz.2]** RPC `get_expert_hub` (SQL, fasety liczone w bazie).
7. **[P1-A cz.2]** batch `page_full_paths(uuid[])` (albo zmaterializowany `full_path`).
8. **[P1-D]** embedding autora w zapytaniu referencji slidera.

### Faza 3 — tydzień 3–4 (bundle i cold start)

9. **[P2-A]** minifikacja bundla SSR (esbuild), echarts poza graf SSR, lazy MCP SDK.
10. **[P2-B]** powrót do zielonych budżetów klienta (wydzielenie `@tanstack` z entry, audyt
    `vite.measure`); dopiero potem obniżanie floorów.
11. **[P2-E]** `edgeTtlCache` na prefetch chrome.

### Miary sukcesu (istniejący RUM + nowy Server-Timing)

- TTFB p75 tras archiwalnych: dziś = pełny render (5–22 RT × RTT); cel po F1: < 100 ms na HIT.
- Hit-rate `x-nes-cache` (HIT+STALE)/(wszystko−BYPASS): cel > 80 % na publicznym ruchu po F2.
- `ssr;dur` p75 dla MISS wpisu: cel < 400 ms po F2 (3 fale → 1–2).
- `check:bundle` zielony (public ≤ 1475 KB, entry ≤ 350 KB) po F3; docelowo public ~1000 KB.

## 6. Ryzyka i zastrzeżenia

- **Nie zmieniać kontraktu anonimowej skorupy** — każda pokusa „SSR-ujmy stan zalogowania" łamie
  współdzielenie cache i wraca do `private, no-store`. Obecny BYPASS na `Authorization`/`sb-*`
  (`documentCache.ts:119-124`) ma zostać.
- Cache API (L2) jest per-colo — publikacja unieważnia przez bump wersji, więc **nie wolno**
  budować klucza bez segmentu wersji; inaczej wraca problem nieświeżych kolonii.
- `manualChunks`/graf chunków klienta jest po incydentach (h3-500, martwa hydratacja —
  `vite.config.ts:41-101`); zmiany bundlingu wyłącznie z gate'ami `check:chunks` + smoke boot-test.
- `minify` dla SSR weryfikować na CI z realnym limitem pamięci (historyczny OOM przy `build:dev`).
- Wyniki pomiarów bundla pochodzą z buildu na tej sesji (zależności z publicznego npm wg
  `bun.lock`); liczby na CI Lovable mogą się minimalnie różnić, rzędy wielkości nie.
