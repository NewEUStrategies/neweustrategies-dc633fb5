# Audyt wydajności zimnego otwarcia: SSR, hydratacja, TTFB, FCP, LCP, CLS, INP (2026-09-20)

Branch: `claude/elegant-ritchie-dirzur`. Baza: `main` w stanie `c708e48` (2026-09-19).

Zakres: cały ekosystem platformy (strona główna, wpisy i strony CMS, archiwa, wydarzenia, kluby, programy, podcasty, tracker, Q&A, sieć kontaktów, profil, panel administracyjny, checkout), nie tylko strona główna. Przedmiot: pierwsze wejście czytelnika bez cache przeglądarki, na zimnym izolacie Cloudflare Workers, z pustymi cache per-izolat.

Charakter: audyt statyczny kodu (HEAD `c708e48`), zestawiony z jedynymi dostępnymi liczbami produkcyjnymi (RUM z 2026-09-17, próbka `curl` z 2026-09-05) oraz z ostatnimi przebiegami CI na artefakcie produkcyjnym (`first-visit` i `lighthouse`, 2026-09-19). Żadna liczba produkcyjna nie została tu zmierzona ponownie: produkcja, produkcyjny projekt Supabase, konektor Lovable, artefakty GitHub Actions i prywatny rejestr pakietów nie były osiągalne z środowiska audytu (szczegóły w §2). Wszystkie twierdzenia o kodzie są przypięte do `ścieżka:linia` w HEAD. Audyt wykonało siedmiu wyspecjalizowanych agentów (dwa zadania krytyczne modelem Fable 5.1, pięć modelem Opus 5), a 18 ustaleń jednoźródłowych przeszło dodatkową kontradyktoryjną weryfikację w kodzie (wyniki w §9).

**Diagnoza w sześciu zdaniach.**

1. Na powierzchniach publicznych FCP równa się TTFB plus 0,24–0,58 s, więc wąskim gardłem jest czas do pierwszego bajtu, a nie CSS, fonty ani skrypty (`docs/RENDEROWANIE_CWV_2026-09-17.md:30-33`).
2. TTFB na zimnym izolacie składa się z czterech szeregowych odcinków: start izolatu z pełnym grafem aplikacji (393 statyczne importy tras, oba słowniki i18n), dwa szeregowe odczyty bazy planem service-role **przed** konsultacją cache dokumentów, loader korzenia z falą ustawień (6 równoległych zapytań, wyczerpujących limit połączeń Workera) i falą chrome (awaitowaną na każdej trasie treści), oraz loader trasy z 1–6 szeregowymi falami zapytań (najwięcej na wpisie), z których każda kosztuje ~142 ms do bazy.
3. Zimny render **niemal nigdy nie zasiewa cache dokumentów**: każde przekroczenie budżetu (400–600 ms na home, 500 ms chrome na pozostałych trasach) ustawia `private, no-store`, a magazyn odrzuca taki dokument i nie odświeża go w tle; przy pustych cache per-izolat budżety są przekraczane z konstrukcji, więc kolejny czytelnik znów płaci pełny render (§4, F02).
4. Cache per-izolat dla ustawień, tokenów, menu i tickera nie ma warstwy współdzielonej w kolonii, choć taka warstwa (Cache API) istnieje i jest już używana dla katalogu tenantów i redirectów (F03); warmer grzeje 4 ścieżki z runnera GitHub (najprawdopodobniej kolonia amerykańska), więc kolonie czytelników w Europie nie są grzane (F12).
5. Po pierwszym bajcie przeglądarka pobiera ~3,07 MB nieskompresowanego JS (563–576 KB gzip domknięcia startowego plus chunk trasy), dokument HTML o rozmiarze od 498 KB (realna treść, 2026-09-06) do 775 KB (produkcja, 2026-09-05; fixture CI 394 KB), w tym 131 KB inline CSS w 49–50 blokach `<style>` niepodlegających cache, oraz `gtag.js` z obcego originu przed jakąkolwiek zgodą; hydratacja jest szeregowo zależna od chunku słownika przez `top-level await` (§5).
6. Największe źródła CLS to szkielet nagłówka o wysokości 64 px wobec ~240 px realnego nagłówka, brak rozgrzania slotów reklamowych w SSR i pięć komponentów `<style>` z danych, z których trzy znikają z SSR po przekroczeniu budżetu i wracają po hydratacji (§6); największe źródła INP to preload trasy przy każdym najechaniu i dotknięciu linku bez opóźnienia, kanał Realtime otwierany dla anonimów na każdym wpisie oraz ~11–15 zapytań PostgREST startujących tuż po hydratacji strony wpisu, do których dochodzi 6–7 zapytań silnika rekomendacji (§7).

**Dlaczego dotychczasowe wdrożenia nie zamknęły problemu.** Repozytorium zawiera 18 dokumentów wdrożeniowych o SSR i wydajności z okresu 2026-07-24 do 2026-09-17; większość naprawiła realne defekty (streaming, budżety, chunking, CLS tytułu, rezerwacje reklam). Żadne nie mogło jednak zmierzyć produkcji: hosting zdejmuje `Server-Timing` i `x-nes-cache`, tryb Lighthouse na wdrożonym URL nigdy się nie uruchomił (zmienna `LHCI_URL` nieustawiona), RUM zbiera dane wyłącznie po zgodzie analitycznej, czyli **nie widzi czytelnika wchodzącego po raz pierwszy**, a harnessy CI mierzą desktop bez throttlingu z bazą-fixture o RTT 40 ms (§3.2–3.3). W tych warunkach każdy budżet SSR został skalibrowany na środowisko, w którym round-trip kosztuje 40 ms, a nie 142 ms.

### 4.2 Ustalenia krytyczne

**F01. Dwa szeregowe odczyty bazy planem service-role stoją PRZED cache dokumentów i są płacone przez każde żądanie, także trafienie.**

- Mechanizm: `redirectMiddleware` (pozycja 5 w łańcuchu) wykonuje `resolveTenantForHost` (katalog tenantów), a po nim `getIndexForTenant` (reguły), każde z terminem 1500 ms; `documentCacheMiddleware` jest na pozycji 10 (`src/start.ts:513-531`). Migawka L2 w Cache API ma `max-age` równy TTL (60 s tenantów, 30 s redirectów) i odczyt odrzuca wpis starszy niż TTL (`bootstrapCache.server.ts:43`), więc chroni wyłącznie izolat rotujący pod ruchem, nigdy po ciszy dłuższej niż minuta.
- Dowód: `src/start.ts:315-347`; `src/lib/server/tenant.server.ts:66,116,134,172-189`; `src/lib/seo/redirects.server.ts:65,109,146,187-206,230-232`; własny komentarz kodu: „TTFB 3 s” (`start.ts:320-331`). Faza `edge-routing` w laboratorium: 86 ms przy RTT 40 ms (2 fale).
- Koszt: 2 × RTT ≈ 0,3–0,4 s typowo, sufit 3,0 s; przy HIT, STALE, MISS i BYPASS.
- Poprawka: (a) rozdzielić świeżość od przetrwania migawki: zapis na 24 h, odczyt nieświeżego wpisu z natychmiastowym serwowaniem i odświeżeniem pod `runAfterResponse`; (b) `homepageLangMiddleware` przed `redirectMiddleware` (F14); (c) `redirectMiddleware` za `documentCacheMiddleware` dla GET HTML z purge dokumentu przy zapisie reguły; (d) docelowo jeden RPC `edge_bootstrap(host)` zwracający tenanta i reguły.
- Ryzyko: nieświeży katalog do bumpu wersji; reguła 301 dla ścieżki w cache dopiero po purge; aktualizacja `src/__tests__/startPipeline.test.ts`.

**F02. Zdegradowany render nigdy nie trafia do cache i nie jest odświeżany w tle, więc zimne otwarcie jest stanem trwałym, nie incydentem.**

- Mechanizm: przekroczenie któregokolwiek budżetu ustawia `resilientCacheControl(true)` = `private, no-store` (`src/lib/ssr/resilientLoad.ts:151-156`; wywołania `__root.tsx:448,604,645`, `index.tsx:249`, `$.tsx:468`). `documentStorePolicy` odrzuca zapis bez `public` + `s-maxage` (`src/lib/http/documentCache.ts:212-229`, warunek w `:220`). Bramka chrome `readChromeWarmup` woła `markDegraded()` **zawsze**, gdy dane nagłówka nie są gotowe przy pierwszym odczycie bramki (`src/lib/ssr/chromeWarmup.tsx:33-36`), także wtedy, gdy `warm()` skończy się sukcesem i nagłówek dostrumieniuje się poprawnie; ten wyścig dotyczy przede wszystkim strony głównej (korzeń nie awaituje tam rozgrzewki chrome), bo na trasach treści `await initialChromeWarmup` (`__root.tsx:614-618`) zwykle domyka dane przed pierwszym odczytem bramki, a degradację wywołuje wtedy wyczerpany budżet 500 ms. `scheduleRevalidation` jest wywoływane wyłącznie z gałęzi STALE (`documentCache.server.ts:726,777`), więc po zdegradowanym MISS nikt nie odnawia wpisu.
- Dowód pośredni z produkcji: własna próba autorów z 2026-09-05: wszystkie odpowiedzi `/` i `/en` to `MISS` z `private, no-store` (`docs/HOMEPAGE_COLD_SSR_2026-09-05.md:75-85`), niewyjaśnione w dokumencie.
- Koszt: na zimnym izolacie budżety 400–600 ms (home) i 500 ms (chrome) są przekraczane z konstrukcji przy 3–6 falach po ~142 ms; pełny render (1–1,6 s) powtarza każdy czytelnik, a L1/L2 kolonii nie rośnie. To najlepsza hipoteza wyjaśniająca „wolno w całym ekosystemie”, a nie tylko przy pierwszym wejściu.
- Poprawka: (a) rozróżnić degradację **treści** (słusznie `no-store`) od degradacji **chrome/tokenów** (nagłówek dostrumieniowany przez Suspense) i dla tej drugiej zapisywać dokument z krótką świeżością (np. `s-maxage=30`); w `chromeWarmup.tsx` nie wołać `markDegraded` gdy `warm()` zakończy się sukcesem przed flushem; (b) w `decorateMissAndDeferStore` (`documentCache.server.ts:497-533`) przy `policy.store === false` z powodu degradacji planować `scheduleRevalidation(request, key)` pod `waitUntil` z limitem prób na klucz, żeby render tła (już z ciepłym `edgeTtlCache`) zapisał czysty dokument; (c) na zimnym izolacie (miss `site_settings` w `edgeTtlCache`) jednorazowo wydłużyć deadline home, bo alternatywą jest droższy render niecache'owalny plus burza refetchów po hydratacji.
- Ryzyko: podwójny CPU na zimno; pętla przy trwale chorej bazie (licznik prób); krótkie okno, w którym kolejni czytelnicy widzą pusty widget spod zgięcia.

**F03. Cache per-izolat dla ustawień, tokenów, menu, tickera i strony głównej nie ma warstwy współdzielonej w kolonii.**

- Mechanizm: `edgeTtlCache` to Map w pamięci izolatu (cap 500 wpisów, TTL 60 s, serve-stale do 5×TTL) bez L2 (`src/lib/ssrCache.ts:5,16,26,34,86-133`). Bootstrap snapshot w Cache API (`src/lib/http/bootstrapCache.server.ts:28-70`) jest używany wyłącznie dla `tenants` i `redirects:<tenantId>`. Klucze decydujące o pierwszym bajcie na każdej trasie (`site_settings_public:all`, `site_design_tokens:row`, `menu-with-items:*`, `trending_posts:*`, `public:home-*`, `public:resolved:*`) są odbudowywane z bazy przy każdej rotacji izolatu.
- Koszt: 6–9 round-tripów w 3 falach na zimnym izolacie, również w kolonii, która ma już ciepły L2 dokumentów; cały koszt F02 jest pochodną tej luki.
- Poprawka: opcjonalny read-through/write-behind w `edgeTtlCache` do `readBootstrapSnapshot`/`writeBootstrapSnapshot` dla białej listy anonimowych kluczy publicznych (klucz `${host}::${key}`, TTL migawki = `ttlMs × STALE_FACTOR`, zapis pod `runAfterResponse`); bump wersji przy zapisie operatora jak w `documentCacheL2`.
- Ryzyko: spójność po zapisie operatora (dziś invalidacja jest best-effort per izolat, `ssrCache.ts:146-151`).

**F04. Koszt zimnego startu izolatu jest strukturalnie duży i niezmierzony.**

- Mechanizm: `getServerEntry()` ładuje cały graf aplikacji; `routeTree.gen.ts` importuje statycznie 393 pliki tras (203 admina), więc kod loaderów, `head()`, `beforeLoad` i importów top-level wszystkich tras jest ewaluowany przy starcie; `src/lib/i18n.ts:101-106` czeka top-level na oba słowniki; 133 overlaye `i18n-*.ts` wykonują `addResourceBundle` przy imporcie; `@react-email/*` przez `routes/platform/email/**` jest w grafie statycznie. Preset Nitro emituje chunki, ale deploy `wrangler` bundluje do jednego skryptu. Jedyny pomiar `server-init` pochodzi z Node (12–22 ms) i nie przenosi się na `workerd`.
- Koszt: rząd 0,1–0,5 s (szacunek); przy p75 `/admin` = 3,15 s dla trasy bez zapytań treści nie da się wykluczyć więcej.
- Poprawka: (1) logować `server-init`, `edge-routing`, `ssr`, `db`, `app` przez `console.log` do Workers Logs i do pierścienia decyzji; (2) `BUNDLE_INVENTORY` dla środowiska serwera; (3) dynamiczne importy ciężkich zależności server-only (`@react-email`, `mammoth`, `xlsx`, `jszip`) w server-fn i server-routes; (4) overlaye i18n admina poza grafem publicznym.
- Ryzyko: zmiana grafu chunków (incydenty 2026-07-20 i 2026-08-06; bramki `check:chunks` i boot-test).

**F05. Fala 1 korzenia zajmuje wszystkie 6 slotów połączeń przy t0, a powierzchnie zalogowane płacą pełne 3000 ms budżetów bez szansy na cache.**

- Mechanizm: R1 = 6 subrequestów (`__root.tsx:371-379,430-438`, `menu.functions.ts:89-98`); loader trasy startuje równolegle i jego pierwsze zapytanie czeka w kolejce. `isClientOnlyDocument` obejmuje wyłącznie `/admin` (`clientOnlyDocument.ts:51`), `showsSiteChrome` wyklucza tylko `/admin` i `/login` (`siteChrome.ts:13`), więc `/profile/*` (24 trasy), `/network`, `/people`, `/reading-list`, `/messages` oraz `/checkout/*` (`checkout.$planId` bez loadera, `checkout.success`, `checkout.cancel`) awaitują R1 (2500 ms) i R2 (500 ms) dla powłoki, której treść renderuje się po hydratacji, a deny-lista (`documentCache.ts:88-104`) wyklucza je z cache.
- Koszt: +0,15–0,3 s kolejkowania na MISS; `/profile/*` 0,7–1,25 s przy każdym twardym wejściu. Doprecyzowanie z weryfikacji: 6 równoległych subrequestów występuje wyłącznie na zimnym izolacie lub po ponad 300 s ciszy na klucz (w stanie ustalonym wszystkie trzy rodziny są serwowane z `edgeTtlCache`), 6 równa się limitowi platformy i nie przekracza go (nadmiar jest kolejkowany, fetch ma deadline 8 s), a 2500 i 500 ms to sufity `withBudget`, nie koszt płacony przy ciepłym cache.
- Poprawka: menu jednym selectem z osadzeniem (`menus?select=…,menu_items(…)`; 4 → 2 połączenia); docelowo RPC `chrome_bootstrap()` (1 round-trip) zasiewający istniejące klucze react-query; trzeci wariant terminu fali 1 dla „chrome bez treści SSR” (np. 800 ms, bez `await initialChromeWarmup`).
- Ryzyko: RLS na osadzeniach; skrócenie budżetu przy chrome przywraca ryzyko F25 (szkielet nagłówka).

**F06. Trasa treści `$.tsx` wykonuje 5–6 szeregowych fal z sufitem 13 000 ms, a jej fala główna ma 7 odnóg przy limicie 6.**

- Mechanizm: `resolve_path` → 7 równoległych zapytań (`src/lib/queries/public.ts:693-708`; runtime Workers kolejkuje 7. subrequest za 6 otwartymi połączeniami, więc to +1 zserializowany round-trip, nie błąd) → profile autorów → SECONDARY (`settleWithinBudget` 3000 ms, `$.tsx:346-388`) startowana dopiero po PRIMARY (`withBudget` 5000 ms, `:267-270`), choć `post_layout_settings` i `related_posts_config` nie zależą od treści → ustawienia. Sufit zamrożony jako „cena stanu” (`src/lib/ci/ssrBudgets.ts:95-111`).
- Koszt: 0,7–0,85 s danych na zimno (5–6 fal × ~142 ms) plus ~0,15 s kolejkowania W1 za sześcioma subrequestami R1 (F05) ≈ 0,85–1,0 s; sufit 13 s przy chorej bazie. Cała rezolucja jest opakowana w `edgeTtlCache` 60 s per izolat (`public.ts:836-838`), więc 7 odnóg płaci zimny izolat lub wygasły wpis, nie każde żądanie; `related_posts_config` nie jest cache'owane i płaci zawsze.
- Poprawka: wspólny `deadlineAt` dla wszystkich faz (wzorzec `homeSsrDeadline`), sufit 1200–1500 ms; start prefetchów SECONDARY przed `await` PRIMARY; scalić `post_tags` i `post_categories` do jednego RPC albo osadzić w `resolve_path` (≤ 5 odnóg); `fetchAccessRule` zdjąć z krytycznej ścieżki anonimowej skorupy; docelowo RPC `resolve_content_bundle(segments)` (wzorzec `get_expert_hub`, migracja `20260724150500`).

### 5.2 Ustalenia

**F17. ### 7.3 Pierwsze interakcje

**F33. `AppLink` uruchamia loader trasy przy każdym najechaniu, fokusie i dotknięciu, bez opóźnienia.** `src/components/atoms/AppLink.tsx:60-99`: `router.preloadRoute({ href })` wołane wprost z `onMouseEnter`, `onFocus` i `onTouchStart`; `defaultPreloadDelay: 50` (`src/router.tsx:76`) dotyczy wyłącznie wewnętrznego handlera `<Link>`, którego `AppLink` nie używa; `defaultPreloadStaleTime: 0` (`:72`, przypięte testem `src/__tests__/router.test.tsx:92`) sprawia, że dopasowanie nigdy nie jest świeże, więc powtórne najechanie powtarza matching, `beforeLoad`, `loader` i przy pierwszym razie import chunku trasy. Na dotyku `touchstart` poprzedza `click` w tym samym geście, więc loader startuje dokładnie w oknie mierzonym jako INP tego dotknięcia. Równolegle Speculation Rules pobierają ten sam dokument. `AppLink` jest użyty w ~68 plikach, `Link` z `@tanstack/react-router` importowany w ~240 — dwie semantyki preloadu w jednym serwisie. Poprawka: debounce 50–80 ms na `mouseenter` z anulowaniem na `mouseleave`; usunąć preload z `touchstart` (lub `pointerdown` z `pointerType !== "touch"`); pamięć ostatnio preloadowanych `href` (TTL 10–30 s); rozważyć `defaultPreloadStaleTime` ≈ 30 s (komentarz „Query owns cache freshness” dotyczy danych, nie pracy routera). Uwaga: semantyka `preloadRoute` wobec `defaultPreloadDelay` wywnioskowana z kodu wywołania, nie ze źródła biblioteki (brak pakietu) — potwierdzić jednym pomiarem w devtools przed wdrożeniem.

**F37. View Transitions z nazwą na każdej karcie wpisu.** `defaultViewTransition: true` (`src/router.tsx:84`) + `viewTransitionName: post-cover-${id}` na każdej karcie (`PostListCard.tsx:126`, `ArchivePosts.tsx:53,76,97`, `variants.tsx:94,104`): `startViewTransition` robi snapshot każdego nazwanego elementu synchronicznie w zadaniu kliknięcia (20+ warstw na archiwum). Brak bramki `prefers-reduced-motion`. Poprawka: nazwa tylko na klikanej karcie (ustawiana na `pointerdown`/`mouseenter`); wyłączenie przy `prefers-reduced-motion`.

Pozostałe: hover na pozycję mega menu montuje `MegaPanel` z `useQuery` (fetch) + `getBoundingClientRect` + portal w jednym zadaniu, a otwarty panel słucha `scroll` w trybie capture, nie passive (`src/components/menu/SiteMenu.tsx:234,239,294-302`); paleta komend `Ctrl+K` jest ograniczona czasem pobrania chunku (cmdk + `i18n-search`); scroll na wpisie ma 6 listenerów passive, z których shrink nagłówka czyta `scrollHeight` w każdej klatce; zmiana języka dociąga drugi słownik (22,5 KB gzip) i re-renderuje wszystkich konsumentów `useTranslation`.

### 7.4 Jak RUM mierzy INP i dlaczego nie widzi zimnego otwarcia

`initWebVitals()` zakłada `PerformanceObserver({ type: "event", buffered: true, durationThreshold: 40 })`, grupuje po `interactionId` i przy < 50 interakcjach raportuje **maksimum** (`src/lib/webVitals.ts:270-303,383`). Wiersz w `web_vitals` to `{metric, value, rating, path, tenant_id}` bez czasu interakcji względem nawigacji, bez `navigationType`, urządzenia ani sieci (`src/routes/api/public/vitals.ts:119-133`), więc nie da się odróżnić INP pierwszej interakcji po boocie od interakcji w 90. sekundzie. RUM startuje wyłącznie po zgodzie analitycznej (`__root.tsx:717-718`) i po `afterPrerendering`, a obserwator rusza po dynamicznym imporcie chunku, więc wczesne interakcje przepadają. Minimalne poprawki: pole `sinceNav` (`entry.startTime` najgorszej interakcji) i `navigationType` w próbce; rozważyć zbieranie samych anonimowych metryk czasowych bez zgody (decyzja DPO); bramka `bootRaw` w `check-bundle-size.ts`.

## 10. Czego nie udało się ustalić i dlaczego

1. **Aktualne produkcyjne p75 TTFB/LCP/INP/CLS i ich rozkład na fazy.** Produkcja nieosiągalna; ostatnie p75 z 2026-09-17 pochodzą z raportu zlecającego; `Server-Timing` nie dociera do przeglądarki i nie jest logowany.
2. **Region projektu Supabase i RTT krawędź → baza.** W repozytorium nie ma tej informacji; jedyny sygnał to ~142 ms/round-trip z jednej próbki. Konektor Supabase nie ma dostępu do projektu `unnltowbgszpdzwpawdu`.
3. **Rozmiar i skład dzisiejszego workera oraz chunku wejściowego.** Brak builda (rejestr 403); ostatni pomiar workera (13 MB / 2,96 MB gzip) jest z 2026-07-24, sprzed wzrostu publicznego JS klienta z 1 541,5 do 2 727,9 KB gzip; `reports/bundle-baseline.json` pochodzi z commitu `2765e53` (2026-09-08), którego nie ma w płytkiej historii.
4. **Czas startu izolatu na `workerd`.** Jedyny pomiar `server-init` (12–22 ms) pochodzi z Node i nie przenosi się na Workers.
5. **Czy L2 (Cache API) działa w runtime hostingu, czy `Link` przechodzi przez hosting, czy zona ma Early Hints i czy `wrangler deploy` inlinuje chunki do jednego skryptu.** Brak `wrangler.*` w repo, brak dostępu do panelu; `docs/HOMEPAGE_COLD_SSR_2026-09-05.md` §5 pkt 5 zapisuje weryfikację L2 jako niewykonaną.
6. **Udział MISS/STALE/HIT/BYPASS w ruchu i częstość rotacji izolatów.** Pierścień decyzji jest per-instancja i bez dostępu; od tej liczby zależy waga F01/F04 (płacone zawsze) względem F02/F05–F07 (płacone na MISS).
7. **Skład dokumentów buildera najemcy** (liczba sekcji, widgetów, unikalnych rodziców w tickerze, terminów słowniczka, slotów reklamowych, ikon spoza zestawu) — dane w bazie; koszty F11, F26, F38, F24 skalują się z nimi.
8. **Semantyka frameworka**: kolejność `load()` → `dehydrate()` → render, gałąź `isbot` → `allReady`, zakres splittera, `preloadRoute` wobec `defaultPreloadDelay`, kolejność emisji `<head>` — potwierdzone komentarzami, testami i skryptami repozytorium, nie źródłem biblioteki (pakiety nieobecne).
9. **Wolumen i jakość danych w `web_vitals`** — bez dostępu do bazy nie wiadomo, czy p75 per trasa ma wystarczającą liczbę próbek; RUM nie zapisuje urządzenia ani stanu cache, więc pytania „czy mobile jest wolniejszy” i „czy zimne jest wolniejsze niż ciepłe” są dziś bez odpowiedzi w danych.

## 11. Załączniki

### 11.1 Odczyt istniejących danych RUM (SQL Editor Supabase, rola `postgres`/`service_role`)

p75 per trasa (sedno zgłoszenia „cały ekosystem”):

```sql
select path,
       count(*) filter (where metric = 'TTFB') as n_ttfb,
       percentile_cont(0.75) within group (order by value) filter (where metric = 'TTFB') as ttfb_p75,
       percentile_cont(0.75) within group (order by value) filter (where metric = 'LCP')  as lcp_p75,
       percentile_cont(0.75) within group (order by value) filter (where metric = 'INP')  as inp_p75,
       percentile_cont(0.75) within group (order by value) filter (where metric = 'FCP')  as fcp_p75,
       percentile_cont(0.75) within group (order by value) filter (where metric = 'CLS')  as cls_p75
from public.web_vitals
where created_at >= now() - interval '7 days'
group by path
having count(*) filter (where metric = 'TTFB') >= 30
order by ttfb_p75 desc nulls last;
```

Agregacja po module:

```sql
select case
         when path ~ '^(/en)?/admin'    then 'admin'
         when path ~ '^(/en)?/events'   then 'events'
         when path ~ '^(/en)?/club'     then 'club'
         when path ~ '^(/en)?/profile'  then 'profile'
         when path ~ '^(/en)?/tracker'  then 'tracker'
         when path ~ '^(/en)?/network'  then 'network'
         when path ~ '^(/en)?/checkout' then 'checkout'
         when path ~ '^(/en)?/blog'     then 'blog'
         when path in ('/', '/en')      then 'home'
         else 'inne'
       end as modul,
       metric,
       percentile_cont(0.75) within group (order by value) as p75,
       count(*) as samples
from public.web_vitals
where created_at >= now() - interval '30 days'
  and metric in ('TTFB','LCP','INP','FCP','CLS')
group by 1, 2
order by modul, metric;
```

Rozkład ratingów TTFB (progi `good ≤ 800`, `needs-improvement ≤ 1800`, `src/lib/observability/vitalsThresholds.ts:16`):

```sql
select rating, count(*), round(100.0 * count(*) / sum(count(*)) over (), 1) as pct
from public.web_vitals
where metric = 'TTFB' and created_at >= now() - interval '7 days'
group by rating order by 2 desc;
```

Sygnały martwej hydratacji:

```sql
select date_trunc('hour', created_at) as h, path, left(message, 120) as msg, count(*)
from public.client_errors
where created_at >= now() - interval '7 days'
  and (message like '[boot]%' or source in ('onerror','unhandledrejection'))
group by 1, 2, 3 order by 4 desc limit 50;
```
